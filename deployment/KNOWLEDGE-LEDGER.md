# 知识账本与合并式主题页（设计提案）

状态：**设计提案**。本文描述可选的知识账本与主题页拆分方案，不表示功能已经实现、获准启用或经过真实部署验收。本文不包含主机的 Wiki 指标、用户选择或运行快照。

## 1. 目标与成功标准

Wiki 要沉淀 agent 工作中的**业务结果**和**用户给出的决定**，让之后的协作少解释、少返工。写入侧需要同时做到：

1. 已确认的决定尽快可用：不因同批其他内容有问题而被整体卡住；
2. 页面连贯：按业务主题组织，而不是每次操作新建一页；
3. 需要人判断的事情足够少，并且确实值得判断。

可考虑的验收指标（应使用经批准的私有或合成数据单独建立基线）：

| 指标 | 基线（截至 2026-09-26） | 目标 |
|---|---|---|
| 会话批次挂起率 | 未提供基线 | 由维护者按目标设置 |
| 已发布知识里 decision + constraint 的占比 | 未提供基线 | 按任务目标观察变化 |
| 新建主题页中“单次事件页”的比例 | 未提供基线 | 新建页以长期主题为主 |
| 检索评测里的相关性与噪音 | 未提供基线 | 不低于经批准的回归基线 |

## 2. 现状

### 两条写入路径

- **旧路径**（`pipeline.ts` 的 `runModels → handleDecisions`）：逐条抽取、逐条审核，通过的 claim 直接发布。没有页面修订的记录在重放时走“追加段落”兼容路径（`materialize-plan.ts` 的 `publicationEntries`），所以页面会被追加成一段段碎片。
- **会话路径**（`consolidate.ts` 的 `consolidateSession`，当前默认）：规划 → 整页编辑（≤ 5 条带原文引用的 claim）→ 结构校验 →（一次纠正）→ **整页独立审核，只给整批一个结论**。页面连贯了，但只要一条 claim 不过关，整批都进不来。

### 挂起原因（可按审核理由分类）

| 类型 | 批次 | 性质 |
|---|---|---|
| 助手自述被写成事实或完成状态 | 未统计 | 可由程序按证据角色确定性降级 |
| 单条 claim 的证据锚点错配或推断过度 | 未统计 | 应尽量只影响该条 claim |
| 整稿结构校验失败（证据不完整、权限不确定） | 未统计 | 应阻止不安全的发布 |
| 待审队列已满 | 未统计 | 应遵循队列容量限制 |
| 引用退役结构、路由或范围 | 未统计 | 部分问题可由程序校验 |
| 真正的冲突或用户意图不明 | 未统计 | **需要人判断** |

按挂起发生的阶段拆分时，可区分审核模型与程序校验/容量限制：

| 类型 | 审核模型阶段 | 程序校验或容量 |
|---|---|---|
| 助手自述被写成事实或完成状态 | 按经审核的样本统计 | 按经审核的样本统计 |
| 证据锚点错配或推断过度 | 按经审核的样本统计 | 按经审核的样本统计 |
| 整稿证据或权限校验 | — | 按经审核的样本统计 |
| 待审队列已满 | — | 按经审核的样本统计 |
| 引用退役结构 | 按经审核的样本统计 | 按经审核的样本统计 |
| 冲突或意图不明 | 按经审核的样本统计 | — |
| 路由、范围及其他 | 按经审核的样本统计 | 按经审核的样本统计 |

若审核模型判 `needs_review` 时直接挂起整批，就可能错过根据审核理由进行有界纠正的机会。应依据当前实现和受审样本核实具体失败模式，不在此记录未验证的数量或运行状态。

### 其他缺口

- **缺少“被取代”的记录**：新决定和旧决定并存时，检索可能需要按日期和状态区分。
- **页面粒度**：按单次操作命名的页面会随着操作次数增长，而不是随长期主题增长。

## 3. 方案

### 3.1 两层结构

```text
会话批次 ──抽取──▶ 候选 claim ──确定性检查 + 逐条审核──▶ 知识账本（不可变记录）
                                                         │
                                  ┌──────────────────────┼──────────────────────┐
                                  ▼                      ▼                      ▼
                          当前决定摘要              检索（段落 + 账本）      主题页合并（整页审核）
```

- **账本层**：每条通过的 claim 成为一条带原文引用的不可变账本条目，发布后立即可以被检索和速查块使用。条目自身不直接渲染成页面段落。
- **页面层**：主题页由账本条目合并生成，沿用现有的规划、编辑、整页审核机制。合并失败只会让页面停留在上一个版本，**账本条目不受影响**。

### 3.2 逐条判定

1. **确定性检查**（程序，不调用模型）：
   - 引文必须逐字存在于冻结的证据中（已有）；
   - 按证据角色约束 kind/status：主证据只有助手陈述时，**自动降级**为 historical lesson，而不是挂起（现在是由纠正步骤处理，失败就挂起）；
   - 必须有决策对象。
2. **逐条审核**：审核输出从整批一个结论改为每条 claim 一个结论（accept / reject / needs_review，附理由）。只有 needs_review 的条目进入人工队列，同批其他条目照常发布。
3. **取代关系**：当新的 decided claim 明确替换同一决策对象上的旧决定，并且有用户原话作为证据时，审核可以在条目上标记 `supersedes: [旧条目 ID]`。被取代的条目仍然保留（可追溯），但速查块和检索会优先使用未被取代的条目。标记只能指向同一项目、同一决策对象的已发布条目，由程序校验。

### 3.3 合并式主题页

- **页面粒度**：一页对应“业务 × 长期主题”，例如“投放结构与预算规则”。单次操作（某天的预算调整、某个素材批次）写进该主题页的**时间线**小节，写明日期、动作和结果，不再新建页面。规划阶段增加约束：新建页面的决策对象必须是长期主题。程序只能可靠拦截明显的日期或批次编号式命名（例如“2026-09-24 …调整”“0918 …素材”），其余由规划约束和独立审核把关。
- **触发时机**：同一主题累计 ≥ N 条新的账本条目，或距离上次合并超过 T 天，就触发一次合并。合并读取该主题的全部有效条目（已排除被取代的），重写整页并独立审核。
- **存量单次事件页**：通过一次**经审核的迁移**并入对应的主题页。迁移沿用现有 `migrate-shared.py` 的哈希校验和备份机制，只由共享写入机执行。

### 3.4 取用

- 检索同时使用主题页段落（叙述和理由）和账本条目（一句话结论），现有项目范围门槛对两者都生效。
- 当前决定摘要可读取账本并应用取代关系，从而优先呈现有效决定。

### 3.5 双机协议与迁移

- 新的记录类型：账本记录只含 claim（以及可选的 `supersedes`），`payload.kind = "ledger"`。新 runtime 重放时不把它渲染成页面段落。
- **旧 runtime 会把它当作旧式 claim 追加进页面**，所以必须能力门控：
  - 新 runtime 在 build manifest 和申报里声明 `knowledge-ledger-v1`；
  - 两台机器都申报后，才能通过共享策略文件启用（做法同 `v2/topic-scope.json`）；
  - 启用前绝不产出账本记录。
- **存量数据是否需要迁移**：应先验证旧发布记录能否按新结构读取；新记录可带上 `kind` 和 `supersedes`。
- 既有待审条目应通过受审重试流程按新规则重新处理，不批量清空状态。

### 3.6 成本

每批的模型调用大致不变：抽取与逐条审核，必要时进行一次纠正。页面合并按主题分摊；实际调用次数与成本需从部署配置及供应商账单核实。

## 4. 分阶段实施

每个阶段是独立的 PR，可以单独验证和回退。

| 阶段 | 内容 | 协议变更 | 验证 |
|---|---|---|---|
| A | 在现有会话路径上：①审核契约改为可修正的问题判 `reject` 并给出改法，进入已有的一次纠正，`needs_review` 只留给冲突和意图不明；②程序校验阶段按证据角色确定性降级；③规划禁止新建单次事件页（程序拦截日期或批次式命名，复用规划纠正）。部署后用现有 `--retry-review` 按新规则重跑已有待审项 | 无 | 重跑待审的救回率；挂起率周环比；新建页类型；现有测试 |
| B | 账本记录类型、`knowledge-ledger-v1` 能力门控、逐条审核、`supersedes`；速查块和检索读取账本 | 有，需双机升级 | 合成用例：同批部分通过；取代关系；旧 runtime 不会收到账本记录；真实副本回放 |
| C | 主题页从账本合并（按 N/T 触发）；存量单次事件页的审核迁移 | 有（沿用 B 的门控） | 页面数和页面粒度；合并失败时账本仍可取用；迁移可回退 |

**阶段 A 不需要改协议**。它针对可由审核理由修正的问题和证据角色校验。纠正本身也可能失败，因此应从经过授权的样本测量结果，不预先承诺救回率。不要采用无限等待队列；待审项长期未处理时，新任务仍须遵守容量限制。

## 5. 风险

- **页面滞后**：页面按 N/T 触发合并，会比现在晚更新；账本条目会先通过检索和速查块提供，弥补这段空档。
- **账本膨胀**：条目数量会比页面多，检索需要去重，速查块已有字符预算。
- **取代关系标错**：被取代的条目只隐藏、不删除，可以撤销；取代必须有用户原话作为证据，并由程序校验范围。
- **双机协调**：另一台机器升级之前，阶段 B 和 C 不能启用。

## 6. 部署前需要单独确认的选择

1. 阶段 A/B/C 的推进顺序与观察周期。
2. 按主题累计多少条新账本条目或经过多少天触发合并。
3. 是否以及如何经审核迁移既有单次事件页，并准备可回退备份。
4. 是否允许审核模型在有用户原话证据时标记取代关系；被取代条目应可追溯。
